## 1. 목표

`cutting-contract-v1` 입력을 받아 guillotine 제약을 지키는 배치를 만들고, 그 결과를 `cutting.optimize` 작업 종류로 queue 에서 실행한다.

이 작업은 화면을 만들지 않는다. **입력 하나가 들어가면 제약 위반 없는 결과가 나오고, 그것이 작업 queue 를 통해 실행되는 것**까지가 범위다. 결과를 사람이 보고 고치는 것은 `P2-B05` 다.

## 4. 사용자 결정이 필요한 항목

### `D2-B04-I` 탐색 예산과 성능 기준 — **확정: (가) 시간 상한 30초**

전략을 몇 개까지 돌릴지, 얼마나 걸려도 되는지다. 재단은 queue 에서 도는 작업이라 몇 초는 문제가 아니지만 상한이 없으면 부품이 많은 수주에서 worker 가 오래 잡힌다.

| 안 | 내용 | 결과 특성 |
|---|---|---|
| **(가) 시간 상한 30초** (권장) | 전략을 순서대로 돌리다 30초를 넘으면 그때까지 최선을 낸다 | 최악의 경우가 정해진다. 큰 수주에서 결과가 전략 순서에 따라 달라질 수 있다 |
| (나) 상한 없이 전 조합 완주 | 12개 조합을 항상 다 돌린다 | 같은 입력에 항상 같은 결과. 부품 수가 커지면 시간이 예측되지 않는다 |
| (다) 부품 수로 조합 수 조절 | 부품이 많으면 전략을 줄인다 | 시간과 결정론을 모두 지키지만 규칙이 하나 늘어난다 |

`D2-B03-C` 결정론을 엄격히 보면 (나)가 맞지만, 실제로 부품 수가 몇 백을 넘는 수주가 있는지는 현장 사정이다.

**2026-08-23 사용자가 (가)를 확정했다.** 표본 3건은 전략 12개를 다 돌려도 4ms 안에 끝나 상한에 닿지 않는다. 상한은 부품이 크게 늘었을 때 worker 가 붙잡히는 최악을 막는 안전장치로만 쓰인다. 첫 전략은 시간과 무관하게 반드시 한 번 돌리므로 상한이 아무리 짧아도 결과는 나온다.

**2026-08-23 사용자가 (가)를 확정했다.** solver 는 kerf 를 조각 분할 폭에 더해 처리하므로, 값만 바꾸면 배치 간격이 그대로 따라간다. kerf `5` 로 두었을 때 이웃 부품이 `600` 이 아니라 `605` 자리에서 시작하는 것을 단위 테스트로 고정했다.
