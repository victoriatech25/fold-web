## 1. 목표

부품과 원판, 회전·결·칼날·trim 제약, 배치 결과를 **제품과 무관한 중립 계약**으로 정의한다. `P2-B04` 신규 solver가 이 계약 위에서 구현되고, 결과 검증도 이 계약으로 한다.

이 작업은 알고리즘을 만들지 않는다. **무엇을 입력으로 받고 무엇을 결과로 내는지, 어떤 결과를 옳다고 볼지**를 먼저 못 박는다. 계약 없이 solver부터 만들면 "맞는 결과"의 기준이 구현에 묻힌다.

| `D2-B03-I` | trim | 원판 4변 trim 을 뺀 영역만 배치에 쓴다. trim 영역은 손실로 집계한다 | 이미 `SheetItem` 기준정보에 있다 |

#### 3.2.1 `rotationPolicy` 는 기준정보와 값이 다르다

`D2-B03-E` 를 처음 쓸 때 "기준정보와 같은 값" 으로 적었으나 **사실과 다르다.** 바로잡는다.

| 위치 | 값 |
|---|---|
| 기준정보 `SheetItem.rotationPolicy` | `FREE` \| `KEEP_GRAIN` |
| 계약 `sheet.rotationPolicy` | `FREE` \| `FIXED` |

**코드는 맞다.** 재단 입력 빌더가 옮기며, 지킬 결이 없으면 `FREE` 로 내린다. 계약이 결(grain)이라는 개념을 모르는 채 "돌려도 되는가" 만 알면 되게 만든 것이 이 차이의 이유다.

### 3.3 재단 방식과 결과

| ID | 결정 | 안 | 근거 |
|---|---|---|---|
| `D2-B03-J` | 재단 방식 | **Guillotine(직선 관통) 제약을 지킨다.** 한 번의 절단은 현재 조각을 끝에서 끝까지 가른다. 검증 함수가 영역을 재귀로 쪼개 보며 확인한다 | 현장 장비가 판을 끝까지 자른다. 계산상 수율이 좋아도 자를 수 없는 배치는 쓸모없다 |
| `D2-B03-K` | 결과 | 원판별 `{ sheetIndex, sheetItemId, placements[{ partId, xMm, yMm, rotated }], usedAreaM2, remnants[] }` 와 전체 요약 `{ sheetCount, totalAreaM2, usedAreaM2, yieldPercent, unplacedParts[] }` | 배치 좌표까지 남겨야 도면·작업지시로 쓸 수 있다. 요약만으로는 현장에서 못 쓴다 |

| `D2-B03-M` | 미배치 | 어떤 원판에도 못 넣은 부품은 실패가 아니라 `unplacedParts` 와 사유로 보고한다 | 부품이 원판보다 큰 경우처럼 입력 자체가 불가능한 상황을 결과로 설명해야 한다 |
| `D2-B03-N` | 검증 함수 | 계약과 함께 `validateCuttingResult(input, result)` 를 만든다. 겹침, 경계 이탈, kerf 미확보, 결·회전 위반, 수량 불일치를 전부 검사한다 | solver 가 무엇을 만들든 이 검사를 통과해야 한다. `P2-B04` 는 이 함수를 기준으로 개발한다 |

## 4. 사용자 결정이 필요한 항목

### `D2-B03-O` 최적화 목표 우선순위 — **확정: (가) 원판 수 우선**

전체 작업계획서에도 `신규 solver의 최적화 목표·허용 편차`가 미결정으로 올라 있다.

| 안 | 우선순위 | 결과 특성 |
|---|---|---|
| **(가) 원판 수 우선** (권장) | ① 원판 수 최소 → ② 수율 최대 → ③ 절단 횟수 최소 | 재료비가 가장 크게 줄어든다. 같은 원판 수라면 수율이 좋은 배치를 고른다 |
| (나) 수율 우선 | ① 수율 최대 → ② 원판 수 → ③ 절단 횟수 | 잔재가 크게 남아 재사용에 유리할 수 있으나 원판을 더 쓸 수 있다 |
| (다) 절단 횟수 우선 | ① 절단 횟수 최소 → ② 원판 수 → ③ 수율 | 작업 시간이 줄지만 재료가 더 든다 |

**2026-08-22 사용자가 (가)를 확정했다.** 알루미늄 원판은 재료비 비중이 크고, 원판 한 장을 덜 쓰는 것이 절단 몇 번보다 금액이 크다. 다만 이건 현장 비용 구조에 달린 문제라 확인이 필요하다.

### `D2-B03-P` 허용 편차 — **확정: (가) 원판 수 동일, 수율 -2%p 이내. 다만 기대값 확보 불가로 당분간 적용 불가**

`P2-B04` solver 결과를 무엇과 비교해 합격으로 볼지다.

| 안 | 기준 |
|---|---|
| **(가) 원판 수 동일, 수율 -2%p 이내** (권장) | 표본과 원판 수가 같아야 하고 수율은 2%p 까지 낮아도 통과 |
| (나) 원판 수 +1 허용 | 표본보다 원판을 한 장 더 써도 통과 |
| (다) 원판 수 동일, 수율도 동일 이상 | 표본보다 나쁘면 전부 불합격 |

**2026-08-22 사용자가 (가)를 확정했다.** 원판 수는 곧 재료비라 물러설 수 없지만, 수율 소수점까지 레거시와 똑같이 맞추라는 것은 알고리즘을 베끼라는 말과 같다. `P0-05`가 정한 `CLEAN_REIMPLEMENTATION` 과 어긋난다.

**다만 이 기준을 지금은 적용할 수 없다.** 레거시가 재단 결과를 저장하지 않고 MFC도 실행할 수 없어 비교 대상이 없다(아래 `Q` 참조). `P2-B04` 는 제약 위반 0건을 합격 기준으로 삼고, 기대값이 확보되면 이 기준을 켠다.

### `D2-B03-Q` 표본 확보 방법 — **결론: 입력 표본만 확보. 기대값은 확보 불가**

완료 기준이 "MFC 표본을 계약으로 표현하고 검증 가능"인데 기대 결과를 확보할 방법이 없다.

**2026-08-22 조사 결과**

레거시 참조 PostgreSQL(`hicomtech.biz`, DB `krsteelfold2`, 스키마 `postgres`, PostgreSQL 9.2.24)에 읽기 전용으로 접속해 확인했다.

| 대상 | 확인 결과 |
|---|---|
| `sellfold` | 140,761건. `lenw`·`lenh`·`qty`·`rawcode` 로 **재단 입력이 모두 있다** |
| `sellfold.qtyraw` (사용 원판 수) | **0건**. 14만 행 어디에도 기록이 없다 |
| `sellfold.calcum2` (면적) | 3건뿐 |
| `sellrawuse` (원판 사용량·잔재) | 모든 DB에서 **0건** |
| `sellplaninfo` | 40건이지만 내용은 재단이 아니라 **절곡 DXF 원문**(`dxfdata`, 38만 바이트) |
| `itemcutinfo`·`itemcutdefault` | 0건 |
| 다른 고객 DB (`cnsteel`, `steelfold_cn_new` 등) | 같은 상태. `steelfold2_org` 는 `qtyraw` 컬럼 자체가 없다 |

`P0-03`이 `sellplaninfo`를 "재단/DXF 관련 표본"으로 적은 것은 이름 기준 추정이었다. 실제로는 **MFC가 재단 결과를 DB에 되돌려 쓰지 않는다.** 화면과 출력물로만 쓴 것으로 보인다.

MFC 프로그램도 현재 실행할 수 없어 표본을 새로 만들 수도 없다.

**결론**

| 항목 | 결정 |
|---|---|
| 입력 표본 | 실제 수주에서 확보했다. `src/domain/cutting/fixtures/legacy-input-samples.json` 에 3건(각 부품 12개)을 담았다 |
| 기대 결과 | 확보 불가. 표본의 `expected` 는 `null` 이고 비교를 건너뛴다 |

표본에는 치수·수량·원판 규격만 담았다. 거래처·현장·담당자와 부품 이름은 옮기지 않았다(`P0-03` 개인정보 정책).

원판 규격은 `rawcate` 에 비어 있어 `item.sizee` 에서 실제로 쓰이는 `1220×2440`·`1220×3000`·`1220×4000` 세 가지를 후보로 넣었다. 칼날 두께는 레거시에 재단용 값이 없어 `0` 으로 두었다. `rawcate.cutv`·`cuta` 는 절곡 연신값이라 칼날과 무관하다. **실제 칼날 두께는 현장 확인이 필요한 남은 항목이다.**
