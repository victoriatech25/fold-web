## 1. 목표

수주 담당자가 기간·거래처·상태·담당자 기준으로 수주를 안정적으로 찾고, 개별 수주의 절곡·계산·승인·생산 상태 변경을 한 화면에서 읽는다. 승인 수주는 목록과 상세에서 생산 요청으로 자연스럽게 이어진다.

## 3. API 계약

```text
GET /api/v1/orders?q=&customerId=&ownerMembershipId=&statuses=&orderedFrom=&orderedTo=&cursor=&limit=
GET /api/v1/orders/:orderId/history?cursor=&limit=
```

- 목록은 `{ items, nextCursor }`, 기본·최대 `25/100`건을 반환한다.
- `statuses`는 comma-separated `SalesOrderStatus` 배열이다.
- 이력은 수주에 직접 연결된 감사 이벤트와 절곡·계산 이벤트의 안전한 요약만 반환한다.

## 7. 승인 시점의 알려진 결함과 처리

코드리뷰에서 확인한 결함이다. 승인 전에 수정하고 회귀 테스트로 고정했다.

| 위치 | 결함 | 조치 |
|---|---|---|
| `listOrdersPage` | 검색어 조건과 cursor 조건이 같은 `where` 객체에 `OR` 키를 중복으로 써서 cursor spread가 검색 조건을 덮어썼다. `수주 더 보기` 2페이지부터 검색어가 무시된 조직 전체 수주가 붙었다. | cursor 조건을 `AND`로 감쌌다. `keeps the search filter on every cursor page` 통합 테스트로 고정한다. |
| `updateOrderFoldItem` | 문서가 바뀌지 않은 저장에서도 서버가 수주를 `DRAFT`로 되돌렸다. 화면은 checksum 비교로 `CALCULATED`를 유지해 상태가 어긋나고, 승인 버튼이 남아 409를 냈다. | 서버도 `documentChecksumSha256` 비교로 계산 무효화 여부를 판단한다. 화면과 같은 기준이라 어긋나지 않는다. |

다음 항목은 결함이 아니라 성능 여유가 줄어드는 자리다. 지금 규모에서는 문제가 없어 P2-B 착수 전에 다시 판단한다.

- `getOrderHistory`가 `AuditEvent.after ->> 'salesOrderId'`를 인덱스 없이 훑는다. 감사 로그는 전 도메인이 함께 쌓는 append-only 테이블이라 오래된 수주의 상세 화면에서 훑는 범위가 계속 늘어난다. 표현식 인덱스를 걸거나 `salesOrderId`를 별도 열로 비정규화하는 방법이 있고, 둘 다 migration이 필요하므로 사용자 결정 뒤에 한다.
