## 1. 목표

조직별 거래처를 검색·등록·수정·비활성화하고, 거래처에 여러 담당자와 고객 현장을 연결한다. 이후 `P2-A06 가격 규칙`과 `P2-A07 수주`가 UUID 참조와 불변 스냅샷을 사용할 수 있는 서버 기준정보를 완성한다.

```text
거래처 목록·검색
→ 거래처 기본정보
→ 담당자 관리
→ 고객 현장 관리
→ 기본 담당자·기본 현장 선택
→ 수주에서 빠른 검색·선택
```

`BusinessSite`는 우리 회사의 본사·공장·지점이고, 이번 작업의 `CustomerSite`는 거래처의 납품·공사 현장이다. UI와 코드에서 둘을 `사업장`과 `고객 현장`으로 구분한다.

## 5. 권장 데이터 계약

### 5.1 `Customer`

| 필드 | 규칙 |
|---|---|
| `id` | UUID PK |
| `organizationId` | 모든 조회·변경의 조직 경계 |
| `code` | 조직별 고유, 신규 웹 자료는 `C000001` 형식 자동 발급, 생성 후 불변 |
| `type` | `SALES`, `PURCHASE`, `TEMPORARY`, `INTERNAL`, `OTHER`; 기본 `SALES` |
| `name`, `normalizedName` | 상호명 필수, 검색용 정규화 이름 서버 생성 |
| `businessRegistrationNumber` | 선택, 숫자/하이픈 정규화 후 조직 내 활성 자료 중 중복 경고 |
| `representativeName` | 대표자명 선택 |
| `phone`, `fax`, `email`, `website` | 대표 연락처 선택 |
| `postalCode`, `addressLine1`, `addressLine2` | 청구·본사 주소 선택 |
| `taxInvoiceEnabled` | 세금계산서 사용 여부, 기본 `true` |
| `memo` | 내부 비고 |
| `active`, `deletedAt` | 비활성 우선, 물리 삭제 금지 |
| `lockVersion` | 수정 충돌 방지, 저장마다 증가 |
| `createdAt`, `updatedAt` | 서버 시각 |

자동 코드는 조직별 카운터를 트랜잭션에서 증가시켜 중복 없이 발급한다. 레거시 이전 자료는 기존 숫자 코드를 문자열로 보존하고 `LegacyMapping`으로 원본 키를 추적한다.

### 5.2 `CustomerContact`

| 필드 | 규칙 |
|---|---|
| `customerId` | 소속 거래처 필수 |
| `customerSiteId` | 특정 고객 현장 담당자일 때만 선택 |

담당자는 없어도 된다. 첫 담당자는 자동으로 기본 담당자가 되고, 다른 담당자를 기본으로 지정하면 기존 기본 담당자는 같은 트랜잭션에서 해제한다.

### 5.3 `CustomerSite`

기존 Prisma의 모호한 `Site` 모델은 아직 실제 코드에서 사용하지 않으므로 `CustomerSite`로 명확히 변경한다.

| 필드 | 규칙 |
|---|---|
| `customerId` | 소속 거래처 필수 |
| `code` | 거래처 안에서 고유, 생성 후 불변 |
| `name` | 현장명 필수 |
| `phone` | 현장 대표 연락처 선택 |
| `postalCode`, `addressLine1`, `addressLine2` | 납품·공사 주소 선택 |
| `isDefault` | 거래처별 활성 기본 현장 최대 1개 |
| `memo` | 현장 비고 |
| `active`, `deletedAt`, `lockVersion` | 비활성·충돌 방지 |

고객 현장은 0개 이상이다. 첫 현장은 자동으로 기본 현장이 되며, 현장이 없는 거래처도 허용한다. 이후 수주에서는 현장을 선택하지 않은 상태를 명시적으로 허용한다.

## 7. API와 화면 계약

### 7.1 Route Handler

```text
GET    /api/v1/customers
POST   /api/v1/customers
GET    /api/v1/customers/:customerId
PATCH  /api/v1/customers/:customerId

POST   /api/v1/customers/:customerId/contacts
PATCH  /api/v1/customers/:customerId/contacts/:contactId
POST   /api/v1/customers/:customerId/contacts/:contactId/default

POST   /api/v1/customers/:customerId/sites
PATCH  /api/v1/customers/:customerId/sites/:siteId
POST   /api/v1/customers/:customerId/sites/:siteId/default
```

목록 응답은 수주 검색에서 재사용 가능한 최소 요약 DTO를, 상세 응답은 거래처·담당자·현장 전체를 반환한다. 모든 변경 요청은 `expectedLockVersion`과 `Origin` 검증을 사용한다.

### 7.2 화면

- 서비스 셸에 `거래처·현장` 메뉴를 `customer.read` 권한으로 표시한다.
- `/customers`: 검색창, 유형·활성 필터, cursor 목록, 신규 거래처 버튼
- `/customers/[id]`: 상단 상태·주 행동, 기본정보, 담당자, 고객 현장
- 모바일에서는 목록과 상세를 별도 화면으로 유지해 가로 밀집을 피한다.
- 비활성 거래처는 수주 선택 기본 결과에서 제외하지만 관리자 검색에서 다시 활성화할 수 있다.

## 9. 테스트 기준

- 같은 조직에서 자동 코드가 중복 없이 순차 발급된다.
- 다른 조직의 거래처·담당자·현장은 조회·변경할 수 없다.
- 동시수정 stale 요청은 `409`와 최신 서버본 정보를 반환한다.

- 기본 항목을 비활성화하면 선택 가능한 다른 항목을 지정하거나 기본 없음 상태가 명확히 표시된다.

- 모바일 390px에서 목록·상세·팝업에 가로 넘침이 없다.
- 기존 도면·템플릿·회사·인증 E2E가 계속 통과한다.

- 세 모델의 `lockVersion` 충돌 감지와 생성·수정·기본 변경 감사 이벤트를 구현했다.
- `/customers`, `/customers/[id]`를 실서비스 셸에 연결했으며 알림·확인은 모두 공통 팝업을 사용한다.
- 정책 단위 4건, PostgreSQL 전체 통합 40건, 거래처 브라우저 E2E 1건을 통과했다. 전체 회귀 결과는 화면 검수 가이드에 기록한다.

사용자는 [P2-A02 화면 테스트 가이드](../P2-A02-screen-test-guide.md)에 따른 화면 검수를 완료했다. 후속 작업은 `P2-A03 재질·두께` 상세계획과 결정 게이트로 진행한다.
