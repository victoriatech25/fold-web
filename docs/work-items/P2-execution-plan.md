## 1. 목표

P2는 P1에서 완성한 절곡 문서·계산·도면 기능을 회사 기준정보와 실제 수주에 연결하고, 승인된 수주가 제작 파일과 생산 작업으로 이어지는 서버 기반 업무 시스템을 완성하는 단계다.

```text
회사·사업장
→ 거래처·현장
→ 재질·두께·계산 규칙·원판·가격
→ 수주 생성
→ 절곡 개정 불변 복사
→ 계산·금액 스냅샷
→ 승인·생산 요청
→ DXF·PDF·재단 작업
→ 이력·감사·운영 검증
```

## 2. 계승하는 확정 기준

- MFC 소스는 사용하지 않으며, 현재 웹 구현·레거시 DB 표본·사용자 업무 검수를 근거로 독립 재구현한다.
- MFC 실행 메커니즘과 화면을 그대로 복제하지 않는다. 웹의 사용성과 서버 운영 구조를 우선한다.
- 입면도는 UI·API·활성 Prisma 업무 모델에서 계속 제외한다. 원본은 이전 단계에서 보관 대상으로만 다룬다.
- 모든 런타임 데이터는 PostgreSQL과 Prisma migration으로 관리하며 SQLite는 사용하지 않는다.
- 대한민국·한국어 단일 언어로 P2를 완료한다. 다국어는 별도 후속 범위다.
- 알림·확인·입력 대화상자는 시스템 팝업 대신 공통 팝업을 사용한다.
- 계산·금액·문서 결과는 사용 당시 입력과 규칙 개정을 불변 스냅샷으로 남긴다.
- 기계 연동 메뉴의 `planned` 자리는 유지하지만 실제 Agent·장비 통신은 P3에서 구현한다.
- 운영 서버, 운영 PostgreSQL/RDS, queue와 object storage 제품은 즉시 확정하지 않는다. 해당 구성요소가 필요한 작업 착수 직전에 사용자가 결정한다.
- 모든 결정과 업무 검수는 사용자 본인이 담당한다.

## 6. 공통 구현 규칙

1. 각 작업 착수 전에 별도의 `P2-XX-*.md` 상세계획을 작성하고 사용자 결정을 받는다.
2. API는 인증 세션, 조직 경계와 permission을 서버에서 검증한다.
3. 변경 API는 낙관적 잠금 또는 명시적 멱등 키를 적용하고 감사 이벤트를 남긴다.
4. 삭제는 참조 관계가 있는 기준정보에서 물리 삭제보다 비활성·soft delete를 우선한다.
5. 금액·치수·중량은 JavaScript 부동소수점에 의존하지 않고 승인 Decimal 정책을 적용한다.
6. 게시·승인된 규칙과 수주 스냅샷은 직접 수정하지 않고 새 개정을 만든다.
7. 사용자 메시지는 공통 팝업을 사용하며 화면 내 필드 오류는 해당 필드 가까이에 표시한다.
8. 목록은 검색·정렬·cursor pagination과 loading·empty·error 상태를 포함한다.
9. PostgreSQL migration은 빈 DB 적용, 기존 DB upgrade와 rollback/복구 절차를 검증한다.
10. 단위→통합→E2E→사용자 화면 검수 순서로 게이트를 닫는다.

| `D2-C08-*` | 운영 서버·PostgreSQL/RDS·배포 방식 | P2-C08 전 | 추후 결정 |

결정되지 않은 후속 항목 때문에 선행 로컬 개발을 멈추지 않는다. 다만 해당 결정이 DB 계약이나 사용자 결과를 바꾸는 작업에서는 구현 전에 멈추고 사용자 승인을 받는다.

## 8. P2 완료 게이트

- `G2-1`: 기준정보가 조직별로 관리되고 절곡 계산에서 게시된 개정을 선택할 수 있다.
- `G2-2`: 수주 생성부터 승인·생산 요청까지 불변 스냅샷과 감사 이력이 연결된다.
- `G2-3`: 승인 수주에서 재단·DXF·PDF·라벨 결과를 재현하고 실패를 재시도할 수 있다.
- `G2-4`: 승인한 레거시 범위가 반복 가능한 importer와 대조 보고로 이전된다.
- `G2-5`: 운영 환경에서 배포·보안·백업 복구·관측·성능·UAT를 통과한다.
- 입면도와 실제 기계 통신이 구현되지 않았음을 완료 보고서에 명시한다.
