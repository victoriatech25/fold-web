## 1. 준비

로컬 개발 DB에 migration을 적용하고 화면 검수 계정을 준비한다. 계정 정보는 [로컬 화면 테스트 계정](./local-screen-test-account.md)에 있다.

```bash
npm run db:migrate:deploy
npm run auth:ensure-local-screen-test-account
```

터미널 두 개를 쓴다. 하나는 웹(`http://localhost:8000`), 다른 하나는 worker다.

```bash
npm run dev
```

```bash
npm run worker
```

worker가 뜨면 다음과 같은 줄이 나온다. `types`에 처리할 수 있는 작업 종류가 보인다.

```json
{"at":"...","worker":"...","event":"worker_started","types":["dxf.export"],"idlePollMs":2000,"retentionDays":90}
```

## 2. 검수 항목

### 2-1. 메뉴와 빈 목록

1. 로그인한다.
2. 상단 모듈 탭에서 `생산·출력`을 고르고 `작업 큐`로 들어간다.

기대 결과

- `생산·출력` 모듈에 `작업 큐`가 있고 눌러서 들어갈 수 있다. 같은 모듈의 `생산·절단`과 `출력·이력`은 `준비 중`으로 보인다.
- 등록한 작업이 없으면 `조건에 맞는 작업이 없습니다.`가 보인다.

`P2-B01`은 기반 작업이라 아직 화면에 "작업 걸기" 버튼이 없다. `dxf.export`는 계약이 실제로 성립하는지 확인하려고 넣은 한 종류이며 아래처럼 API로 등록한다. 사용자용 진입 버튼은 이 queue를 쓰는 `P2-B04` 재단, `P2-B07` PDF, `P2-B09` 대량 DXF에서 붙는다.

### 2-2. 작업 등록과 진행 확인

먼저 `템플릿` 화면에서 게시된 절곡 개정 하나의 ID를 확인한다. 주소창의 개정 ID를 쓰면 된다.

브라우저 개발자 도구 콘솔에서 다음을 실행한다. 서버가 요청 출처를 검사하므로 반드시 서비스 화면에서 실행해야 한다.

```javascript
await (await fetch("/api/v1/jobs", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({
    type: "dxf.export",
    payload: { revisionId: "게시된 절곡 개정 ID" },
    idempotencyKey: "check-1",
  }),
})).json();
```

기대 결과

- 응답 `status`가 `QUEUED`이고 응답 어디에도 `payload`가 없다.
- `작업 큐` 화면에 `제작 DXF 생성` 항목이 `대기 중`으로 나타난다.
- worker 터미널에 `job_processed` 줄이 찍힌다.
- 화면이 자동으로 갱신되어 `완료`로 바뀐다. 새로고침하지 않아도 된다.
- 완료 항목을 펼치면 `checksumSha256`, `sizeBytes`, `entityCount`가 보이고 `contentRetained`가 `false`다. 파일 바이트 보관은 `P2-B02` 범위다.

### 2-3. 같은 요청을 두 번 보내도 작업은 하나다

2-2를 `idempotencyKey`만 그대로 두고 다시 실행한다.

기대 결과

- 두 번째 응답의 작업 ID가 첫 번째와 같다.
- `작업 큐` 목록에 항목이 하나만 늘어 있다.

### 2-4. 실패한 작업의 사유와 다시 실행

2-2에서 `revisionId`를 존재하지 않는 UUID로 바꿔 실행한다.

기대 결과

- 작업이 `실패`가 되고 빨간 상자에 `DXF로 출력할 절곡 초안을 찾을 수 없습니다.`가 보인다.
- 시도 횟수가 `1/3`에서 멈춘다. 다시 시도해도 결과가 같은 오류이므로 재시도하지 않는다.
- `다시 실행` 버튼이 보인다. 누르면 확인 팝업이 뜨고, 승인하면 다시 `대기 중`이 된다.
- 다시 실행한 뒤 시도 횟수가 `0`부터 시작한다.

### 2-5. worker가 죽어도 작업이 사라지지 않는다

1. worker 터미널을 끈다.
2. 2-2로 작업을 하나 등록한다. `대기 중`에 머무는 것을 확인한다.
3. worker를 다시 켠다.

기대 결과

- worker가 뜨자마자 밀려 있던 작업을 처리한다.
- 작업이 사라지거나 두 번 처리되지 않는다.

### 2-6. 취소

1. worker를 끈 상태에서 작업을 하나 등록한다.
2. `작업 큐`에서 `취소`를 누르고 확인 팝업을 승인한다.
3. worker를 다시 켠다.

기대 결과

- 작업이 즉시 `취소`가 된다.
- worker를 켜도 취소된 작업을 가져가지 않는다.

### 2-6-1. 상태로 좁혀 보기

`작업 큐` 화면 위쪽 상태 줄에서 `실패` chip 을 누르고 `조회`를 누른다. 여러 chip 을 동시에 켤 수 있다.

기대 결과

- 고른 상태의 작업만 남는다. `전체` chip 을 누르면 조건이 풀린다.

### 2-7. 남의 작업은 보이지 않는다

`admin.manage` 권한이 없는 다른 계정으로 로그인해 `작업 큐`를 연다.

기대 결과

- 자신이 등록한 작업만 보인다.
- 조직 관리자 계정에서는 조직 전체 작업이 보인다.

### 2-8. 좁은 화면

브라우저 폭을 390px로 줄인다.

기대 결과

- 가로 스크롤이 생기지 않는다.
- 상태 배지, 진행률, 버튼이 세로로 자연스럽게 쌓인다.
- 상태 chip 이 줄바꿈되어 쌓이고 `조회` 버튼이 잘리지 않는다.
