## 2. 서비스 전체 검토와 반영

로그인 이후 전 화면을 훑고 서버 코드와 문서를 함께 봤다. 지적 18건 중 17건을 반영했다.

서버 쪽 기초에는 문제가 없었다. 라우트마다 권한 확인 → 변경 요청은 출처 확인 → 거부는 감사 기록까지 예외 없이 같은 모양으로 돌아가고, `TODO` 도 남은 `console.log` 도 없다. **어긋난 것은 거의 전부 화면이 사용자에게 하는 말이었다.**

### 2.1 말이 틀린 것

| 자리 | 무엇이 틀렸나 |
|---|---|
| 수주 절곡 작업 카드 | `계산 전` 이 문자열로 박혀 있어 승인까지 끝난 수주에서도 계산 전이라 했다. 옆 탭은 계산 완료라고 하고 있었다 |
| 재단 승인 취소 팝업 | `cc78411` 에서 걷어낸 잔재 동작을 그대로 약속했다. 되돌릴 수 없는 작업 직전 문구다 |
| 업무 홈 | 수주를 `준비 중` 카드로 두었다. 메뉴에서는 열리고 실제 수주가 들어 있었다 |
| 재단 개정 이력 | 상태가 `SUCCEEDED` 로 나왔다. 한글 사전이 이미 있는데 그 자리만 안 썼다 |

계산 상태는 이제 계산 snapshot 을 작업별로 찾아 `계산 완료 · 면적/개` 또는 `재계산 필요` 를 쓴다. 업무 홈은 수주를 실제 링크로 열고 진행 중·생산 중 수주 수를 함께 센다.

### 2.2 찾기

- `matchesPath` 가 접두사로만 맞춰 `/cutting/usage` 에서 `생산·절단` 까지 현재로 켜졌다. 형제 경로가 있으면 더 긴 쪽을 현재로 본다. 회귀 테스트 5건을 붙였다
- 모듈 탭의 `aria-current` 는 화면이 아니라 구역이므로 `location` 으로 낮췄다. `page` 는 화면 메뉴만 쓴다
- 생산·절단 목록에 조회조건이 없었다. 수주번호 검색과 상태 chip 을 붙였다. 자동 갱신도 같은 조건으로 다시 읽는다
- 재단 상세 제목의 수주번호를 수주 상세로 이었다. 수주 → 재단 길만 있고 돌아오는 쪽이 끊겨 있었다
- 수주 목록의 정렬 기준(`updatedAt`)이 열에 없어 순서가 무작위로 보였다. `최근 변경` 열을 넣었다
- 감사 로그의 작업·대상 유형이 내부 코드 자유입력이었다. 카탈로그에서 분류별 select 를 만들었다

### 2.3 읽기

- 작업 큐가 성공한 작업마다 원시 JSON 을 펼쳐 놓았다. `details` 로 접었다
- 읽기 전용 수주를 저장 상태 문구로만 알렸다. 자물쇠 배너로 올리고 비활성 입력 대비를 키웠다
- 좁은 화면에서 조회조건이 세로로 다 펼쳐져 목록 첫 줄이 1,400px 아래에 있었다. 공통 `QueryBar` 를 lg 미만에서 접는다
- 로그인 안내 자리에 투명 글씨가 남아 보조기기가 읽었다. 내용을 비웠다

### 2.4 기준

- **원판 사용 실적 조회 경계를 KST 로 고정했다.** 서버 로컬 시간대를 따르고 있어 배포 환경에 따라 집계가 하루씩 밀 수 있었다. 감사 로그가 이미 쓰던 기준이다. **수주는 손대지 않았다** — 한국 날짜를 UTC 자정에 저장하는 규칙이라 조회 경계가 이미 맞는다
- 검수 가이드 포트를 8000 으로 맞추고 메뉴 표를 현재 3단 구조로 다시 썼다. `npm run dev` 가 8000 을 고정하는데 README 가 가리키는 문서는 3001 이라고 적혀 있었다. 옛 `P2-A0x` 가이드에는 포트 안내만 남겼다
- `잔재 보관 기준` 을 `남는 조각 표시 기준` 으로 바꿨다. 다시 쓰지 않기로 했는데 보관 기준을 받는 것처럼 보였다. 값의 쓰임은 그대로다

| 항목 | 결과 |
|---|---|

| 2-6 권한 | 통과. 화면도 숨기고 API 도 `403` 이다 |

### 3.1 결함 하나 — 승인 취소 뒤 재승인이 항상 500

**`D2-B06-F` 와 유일 제약이 정면으로 부딪히고 있었다.**

`D2-B06-F` 는 승인을 취소해도 실적을 지우지 않고 무효로 남긴다. 그런데 유일 제약 `(cuttingPlanRevisionId, sheetKey)` 는 상태를 가리지 않아 무효가 된 줄이 자리를 계속 차지했다. 그래서 같은 개정을 다시 승인하면 반드시 유일 제약 위반으로 실패했다.

코드 주석에 `같은 개정을 두 번 승인하는 길은 없지만` 이라고 적혀 있었는데 **길이 있었다.** 승인 취소는 재단을 `계산 완료` 로 되돌리고 그 화면의 `승인` 버튼은 그대로 눌린다. 사용자가 보는 것은 `서버에서 재단 요청을 처리하지 못했습니다.` 뿐이고 빠져나갈 길(`다시 계산`)은 화면 어디에도 안내되지 않았다.

**겹쳐 쓰기를 살아 있는 실적에만 막도록 좁혔다**(`20260905030000_sheet_usage_active_unique`). 무효 이력은 몇 겹이든 쌓이고 활성은 항상 하나다. 이력 보존과 이중 승인 방지를 둘 다 지킨다.

부분 유일 인덱스는 Prisma 스키마로 표현되지 않아 migration SQL 에만 있다. `PriceBook`·`PriceTier`·`SheetItem` 이 이미 쓰는 방식이고 `db:migrate:check` 는 드리프트로 잡지 않는다. 적용할 때 한 번 걸렸는데, Prisma 가 이걸 인덱스가 아니라 **테이블 제약**으로 만들어 둬서 `DROP INDEX` 가 아니라 `DROP CONSTRAINT` 여야 했다.

통합 테스트에 `승인을 취소한 개정을 다시 승인할 수 있다` 를 넣었다.

### 3.2 결함 둘 — 원판 필터 해제가 주소에 반영되지 않았다

`원판 필터 해제` 가 화면 상태만 바꾸고 주소의 `?sheetItemId=` 를 남겨 두었다. 새로고침하면 필터가 되살아나고, 링크를 받은 사람은 보낸 사람과 다른 화면을 봤다. 해제할 때 주소도 함께 지운다.

### 3.3 검수 중 함께 반영한 화면 개선

- 수주 실적 표에 **상태 배지**(`사용`/`무효`)와 **취소 사유**, **참고 원가 열**을 더했다. 취소선이 유일한 단서라 보조기기로는 두 줄을 구분할 수 없었다. UI 기준선 6항이 색만으로 상태를 전하지 말라고 한 것과 같은 성격이다
- 실적이 없는 기간에 **총계 줄을 감춘다.** `수율 0%` 는 "재단했는데 하나도 못 건졌다" 로, `참고 매입원가 0원` 은 "공짜로 썼다" 로 읽힌다
- 수주 화면 총계도 살아 있는 실적에 원가가 하나도 없으면 항목 자체를 뺀다
